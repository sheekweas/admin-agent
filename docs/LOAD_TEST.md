# Нагрузочные и конкурентные испытания (ТЗ §21, §22.1 «Load»)

Дата: 14.11.2026. Скрипты: `scripts/load/` (httpx + asyncio, без новых зависимостей), инструкция —
`scripts/load/README.md`. Сырые результаты каждого прогона — `scripts/load/results/*.json`.

## Окружение

| Параметр | Значение |
|---|---|
| Хост | Windows 11 Pro, Docker Desktop 29.9 (WSL2), 16 vCPU, 15.5 GiB RAM для Docker |
| Стек | `docker compose` из репозитория: `api` (1 процесс uvicorn, без `--workers`), `worker` (Celery, concurrency 4), `beat`, PostgreSQL 16, Redis 7 |
| Режимы | `LLM_PROVIDER=mock`, `WHATSAPP_MODE=mock`, `TELEGRAM_MODE=mock`, `VOICE_PROVIDER=mock` — внешние вызовы исключены, как требует §21 |
| Данные | демо-организация «Barber KZ» (`python -m app.seed`): ~165 контактов, ~160 броней, ~270 лидов, 66 платежей (+ данные предыдущих прогонов) |
| Пул БД (API) | `DB_POOL_SIZE=10`, `DB_MAX_OVERFLOW=20` (новые настройки, по умолчанию; было 5 + 10 — см. дефекты) |
| Клиент нагрузки | тот же хост, `localhost:8000` (сеть не учитывается) |

Важно: в mock-режиме WhatsApp AI-ход выполняется **внутри процесса API** (BackgroundTasks), а не в Celery —
это худший случай для подтверждения вебхуков. В `live` AI уходит в Celery и ACK будет быстрее.

| # | Дефект (как найден) | Причина | Исправление | Регрессия |
|---|---|---|---|---|
| L1 | Параллельные запросы с **одним** `Idempotency-Key` → 14 из 20 получали 409 (slot_race) | Запрос, ждавший блокировку мастера, видел слот занятым «своей же» бронью и бросал `SLOT_UNAVAILABLE`, не перепроверив ключ | `services/booking.py::create_booking`: перед 409 повторно ищем бронь по ключу | `test_stage3_regressions.py::test_concurrent_same_idempotency_key_returns_one_booking` |
| L2 | 500 и тайм-ауты 30 с при всплеске вебхуков (`QueuePool limit of size 5 overflow 10`) | Доставка сообщения клиенту запускалась в `after_commit`, когда сессия ещё держит соединение → 2 соединения на поток; 40 потоков против пула 15 | Доставка перенесена в `after_transaction_end` корневой транзакции (соединение уже возвращено); пул настраивается `DB_POOL_SIZE`/`DB_MAX_OVERFLOW` (10/20) | `test_stage3_regressions.py::test_post_commit_delivery_does_not_hold_a_second_pooled_connection` |

| E1 | (E2E) Сообщения клиенту из воркера (напоминания, подтверждения, SLA) оставались `queued` до 60-секундного «подметания» | SQLAlchemy вызывает `after_commit` и при RELEASE SAVEPOINT; хук отправлял до настоящего COMMIT и терял id | Хук игнорирует вложенные транзакции | `test_stage3_regressions.py::test_message_queued_inside_savepoint_is_delivered_after_outer_commit` |

## Замечания (не дефекты, к сведению)

- ACK вебхука в mock-режиме 1.4–1.9 с p95 при 50 параллельных — из-за AI-хода внутри процесса API. Для
  продакшена (`WHATSAPP_MODE=live`) AI-ход уходит в Celery; при росте нагрузки — несколько процессов uvicorn
  (`--workers`) и учёт `max_connections` PostgreSQL (≈ процессы × (DB_POOL_SIZE + DB_MAX_OVERFLOW)).
- Гонка за слот сериализуется блокировкой строки мастера: 50 одновременных запросов на один слот завершаются
  за ~1.7 с (каждый проигравший получает подборку альтернатив) — ожидаемо и приемлемо.
- Уведомления, созданные обработчиком outbox, отправляются на следующем тике (`now` вычисляется в начале
  тика) — задержка ≤ интервала beat; повторов не вызывает.
- Скрипты создают в демо-организации данные (контакты `+7708…` из всплеска, отменённые брони гонки) и
  перенастраивают `app_secret` интеграции WhatsApp на случайный — секреты в отчёты не выводятся.
